# 综测记录发布指南

本文是一份面向仓库维护者的操作指南，用于验证并发布 Windows 稳定版本。示例以 `v0.1.0` 为例；其他版本应替换为对应的 SemVer。

## 前置条件

- Windows 10/11 x64
- Node.js 24.18.0、pnpm 11.20.0、Rust 1.97.1（含 `rustfmt` 和 `clippy`）
- GitHub CLI 已登录且对 `GodBook/zongce-records` 有写权限
- 受保护的 `release` Environment 已配置发布审批；GitHub Secrets 已配置 `TAURI_SIGNING_PRIVATE_KEY` 和 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`
- 更新签名私钥的仓库外恢复副本可用，但日常发布不应读取或移动它

本机恢复副本默认位于 `%USERPROFILE%\.tauri\综测记录\`。该目录不得加入仓库、压缩进发布附件或粘贴到 Issue/日志中。

## 1. 确认版本一致

以下位置必须使用相同的不带 `v` 的版本号：

- `package.json` 的 `version`
- `src-tauri/Cargo.toml` 的 `package.version`
- `src-tauri/tauri.conf.json` 的 `version`

标签使用带 `v` 的形式，例如 `v0.1.0`。

## 2. 执行发布前验证

在仓库根目录运行：

```powershell
pnpm install --frozen-lockfile
pnpm check
pnpm version:check
pnpm build
pnpm test:e2e
cargo fmt --manifest-path src-tauri/Cargo.toml --all -- --check
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets --locked -- -D warnings
cargo test --manifest-path src-tauri/Cargo.toml --all-targets --locked
cargo test --manifest-path src-tauri/Cargo.toml --locked performance_5000 -- --ignored --nocapture
node node_modules/@tauri-apps/cli/tauri.js build --ci --config src-tauri/tauri.ci.conf.json -- --locked
```

该命令生成不含更新签名产物的本地安装器，不需要也不会读取私钥。检查 `src-tauri/target/release/bundle/nsis/` 中的当前用户级安装器，并使用普通 Windows 用户验证：

- 安装过程不请求管理员权限；
- 安装和卸载界面使用简体中文，且旧版本安装器不能覆盖新版本；
- 首次启动能创建数据库和默认类别；
- 新增记录、附件归档、统计、Excel 导出和完整备份可用；
- 卸载不会删除用户数据；
- 重新安装后原记录仍可读取。

> [!NOTE]
> 首版没有 Authenticode，SmartScreen 可能显示“未知发布者”。这是已知发布限制，不应通过关闭 Tauri 更新签名来规避。

## 3. 提交并推送

确认没有密钥、数据库、备份或测试导出物进入暂存区：

```powershell
git status --short
git diff --check
rg -n --hidden -g '!node_modules' -g '!src-tauri/target' 'BEGIN .*PRIVATE KEY|github_pat_|ghp_' .
git add -A
git diff --cached --check
git diff --cached --stat
git status --short
git commit -m "release: 发布综测记录 v0.1.0"
git push -u origin main
```

工作流中出现的 `TAURI_SIGNING_PRIVATE_KEY` 变量名是预期配置，不代表私钥内容；重点检查上述命令是否输出实际密钥或令牌值。

等待“持续集成”工作流成功。失败时修复同一个提交线上的问题，不创建发布标签。

## 4. 创建稳定版标签

```powershell
git tag -a v0.1.0 -m "综测记录 v0.1.0"
git push origin v0.1.0
```

标签必须指向 `main` 已包含的提交，并与三个应用版本完全一致。标签会触发“发布 Windows 安装包”工作流；受保护的 `release` Environment 通过审批后，工作流使用 GitHub Secrets 签名更新产物，并创建 Draft GitHub Release。

## 5. 核对发布资产

Draft Release 至少应包含：

- Windows x64 NSIS 安装器；
- Tauri 更新包；
- 对应的 `.sig` 签名；
- `latest.json`；
- 可读的中文发布说明。

检查 `latest.json` 的版本、平台下载地址和签名字段。下载地址必须属于当前仓库的公开 Release，不能指向本机构建路径或临时地址。

下载并校验 Draft 中的安装器和更新资产后再公开：

```powershell
gh release view v0.1.0 --json isDraft,tagName,assets
gh release edit v0.1.0 --draft=false
```

公开后重新请求 Release 下载地址与 `latest.json`，确认无需登录即可访问。

## 6. 验证真实更新

构建一个仅用于测试的 `0.0.0` 本地版本，创建至少一条记录和一份附件，再通过设置页检查更新并升级到公开的 `v0.1.0`。验证：

- 版本号变为 `0.1.0`；
- 记录、类别、附件和自定义数据位置不变；
- 下载中断后可以重试；
- 断网只显示更新失败，不影响记录操作；
- 篡改更新包或签名后安装被拒绝。

测试版本不能推送到 `main`，也不能覆盖公开标签。

## 发布失败与回滚

如果标签工作流失败，先保留失败日志，修复后删除远端失败标签并用同一版本重新触发；只有在该标签尚未形成可用公开 Release 时才这样做。如果已有用户可能下载该版本，则递增补丁版本，禁止移动现有标签。

若公开版本存在严重问题：

1. 在 GitHub Release 中明确标记受影响版本；
2. 暂停或撤下对应 `latest.json` 资产，避免继续自动分发；
3. 修复后发布新的补丁版本；
4. 不用旧二进制覆盖原标签资产。

更新签名私钥一旦疑似泄露，应立即停止发布、轮换密钥、更新应用内公钥，并通过可信渠道发布迁移版本。仅更改 GitHub Secret 不能让已安装客户端自动信任新公钥。
